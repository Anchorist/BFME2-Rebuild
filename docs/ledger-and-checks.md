# Ledger and checks

The ledger is `config/map.json`. Each row identifies a reference item by its
**relative virtual address**, its offset from the executable image base. The
row records its extent, section, role, accepted symbol names, owner and evidence.
One role marks an owned function. Other roles describe things such as shared
emitted code, folded identities and compiler-generated contributions. The
`expected/` sidecar for a translation unit records expected emitted rows and
separate files can describe its neighboring ranges. Assignments and boundaries
can be hypotheses even when the function matches.

## Find a row and its owner

Search the exact RVA in tracked source first. The owning translation unit
usually has a generated `// FUNCTION: BFME2` annotation. For a ledger
lookup, match `rows[].rva` and read `object_id`, `name`, and
`accepted_names`. Match that ID with `objects[].object_id` for the
recorded object path and its placement evidence. The original-path
hypothesis can differ from the tracked annotation owner.

```sh
git grep -n -F '0x00253390' -- src include
python3 -c 'import json; d=json.load(open("config/map.json")); rows=[r for r in d["rows"] if r["rva"]=="0x00253390"]; print(*rows, sep="\n"); ids={r["object_id"] for r in rows}; print(*[(o["object_id"],o["path"]) for o in d["objects"] if o["object_id"] in ids],sep="\n")'
```

That example points to `src/unk/O0024EEBB.cpp`. The expected-file path is
`expected/unk/O0024EEBB.cpp.json`. Replace the `src/` prefix with `expected/`
and append `.json`. A neighboring-range file uses `.neighbours.json`.
The expected-file rows describe additional emissions. The main ledger
and the owning annotation can identify a function even when the expected
file has no row for it. If the ledger, source and worklist disagree, report
the discrepancy rather than changing the annotation.

## Read a generated annotation

Many source files open with lines that the maintainers' generator wrote
from the ledger. The generator is a maintainer tool and is not in this
repository. For example:

```cpp
// Generated by gen_repo.py; map snapshot 3a961c89...
// object=O0030B395 name-evidence=W name-tier=W
// FUNCTION: BFME2 0x0033162B size=21 name=?rva0033162B@Rva0033162B@@QAEXM@Z evidence=?:placeholder tier=B hypothesis:mm1-gap-unit
```

- `map snapshot`: The digest of the map used when the source skeleton was generated. Some files say
  `Generated by gen2b publish 3b` instead (an internal name for the same
  generator); it means the same.
- `object=` is the ledger object (`objects[].object_id` in `config/map.json`)
  that this file stands for. `name-evidence` and `name-tier` say where the
  file's name comes from (table below).
- `FUNCTION`: A ledger row giving a native body address, its extent in bytes, and its current accepted name. `size` is that extent and
  `name` the accepted, compiler-encoded name. A `FUNCTION` line with no body
  below it is an empty attachment: a ledger anchor with an implementation still to be supplied in this translation unit.
- `evidence=P:note` gives the evidence for the function's name: a one-letter
  kind, a colon, and a note.
- `tier` grades the row's placement in this file, and `hypothesis:` names the
  placement rule that put it here. Placement is a hypothesis even when the
  function matches; a better-evidenced file is a welcome correction (ask
  through a ledger change).

`tier` on `FUNCTION` lines:

| Value | Meaning |
| --- | --- |
| `A` | Structural row membership together with a file identity evidenced in the game or WorldBuilder. |
| `B` | A retained or proposed row placement whose supporting evidence is recorded separately. |
| `L` | Structural row membership together with an evidenced upstream library file. |

`name-tier` and `name-evidence` on the `object=` line:

| Value | Meaning |
| --- | --- |
| `E` | An expert-supplied file or library path recorded in the map overrides. |
| `F` | An original filename referenced by the retail game code, such as a diagnostic or assertion path. |
| `L` | A filename attributed by the matched upstream library stream. |
| `W` | A WorldBuilder filename joined to the corresponding game function. |
| `Z` | A filename inferred from a matched Zero Hour donor, retained as a path hypothesis. |
| `invented` | A generated filename for a unit whose original pathname remains open. |
| `library` | The source-header spelling for the upstream-library filename class. |

The letter before the colon in `evidence=`:

| Value | Meaning |
| --- | --- |
| `?` | The function name or unit attribution is unresolved. An address-based spelling is a placeholder. |
| `L` | The following note records a library-source or upstream symbol attribution. |
| `N` | The function name came from the existing reference ledger. |
| `P` | The following note records provisional evidence for the function identity. |
| `S` | The following note records strong evidence for the function identity. |
| `X` | The following note records a checked identity or an independently supported correction. |

The note after the colon:

| Value | Meaning |
| --- | --- |
| `F` | A file path found in the retail build accompanies the attribution. |
| `L` | The attribution uses the upstream library stream. |
| `W` | WorldBuilder evidence accompanies the attribution. |
| `Z` | The attribution uses a matched Zero Hour donor as a hypothesis. |
| `invented` | A synthesized spelling or pathname denotes an unresolved identity. |
| `ledger` | The accepted name comes from the reference ledger. |
| `map` | The note cites the row's current ledger identity or placement. |
| `placeholder` | A generated name stands in while identity evidence is gathered. |
| `proven` | The cited witness resolved the identity under the stated scope. |
| `provisional` | The note states an identity hypothesis with a bounded witness. |
| `retail` | The cited evidence comes from the reference game build. |
| `strong` | Independent observations agree on this identity in the scope described by the note. |
| `vendored=<lib-ver>` | The cited body or symbol is attributed to the named upstream library release. |

`hypothesis:` values. The `mm1-` placement rules extend or choose a
neighbouring unit and name the clues that decided it:

- `mm1-contiguity-<clues>`: address order extends a neighbouring unit from
  an anchor where the clues hold.
- `mm1-neighbour-<clues>`: the neighbouring unit was chosen because the
  clues hold.

Several clues are joined with `+` (for example
`mm1-neighbour-callers+class`). The clues:

| Clue | Holds when |
| --- | --- |
| `callers` | All known referring functions lie in that neighbour. |
| `class` | The other owned rows with the evidenced class lie in that neighbour. |
| `shared-data` | The other references to shared non-literal data come from that neighbour. |
| `pointers` | The other code pointers in the same data record target that neighbour. |
| `pointers-mixed` | The shared data record has code pointers into that neighbour and none into the opposite neighbour. |
| `libfile` | The upstream library match places it in the same upstream source file. |

The other `hypothesis:` values:

| Value | Meaning |
| --- | --- |
| `K` | Callers or reference edges support assigning the row to an inferred object. |
| `Z` | A matched Zero Hour donor supports this placement hypothesis. |
| `assert-inl-unit` | An assert names a shared inline source and the surrounding local rows form a proposed unit. |
| `cohesion` | Same-class membership or literals with one referring group support this placement. |
| `contradicted-by-W` | The current row grouping is retained with a conflicting WorldBuilder file clue recorded. |
| `init-votes` | Initializer references supply the placement vote. |
| `legacy-membership` | The generator carried forward an existing row assignment because finer membership evidence was unavailable. |
| `legacy-preserved` | The generator preserved a populated or leased source unit and its existing row assignments. |
| `mm1-file-string-path` | A retail filename string linked from the function names its proposed source file. |
| `mm1-fragment-path-elsewhere` | A short disconnected stretch remains in its own unit although a file-name clue points elsewhere. |
| `mm1-gap-unit` | An unresolved stretch is kept in one address-named unit, split at incompatible alignment or exception prologue boundaries. |
| `mm1-held-object-encloses-file` | The inferred object spans the row and the full known row range of an existing named file. |
| `mm1-held-object-encloses-unk-file` | The inferred object spans the row and an existing address-named file inside its proposed range. |
| `mm1-held-object-same-path` | The inferred object spans the row and an existing file with the same proposed path. |
| `mm1-libs-upstream-path` | A library match identifies the upstream source file. |
| `name:E` | The unit name comes from a documented expert path or library override. |
| `name:F` | The unit name is supported by a filename cited in the retail game. |
| `name:L` | The unit name comes from upstream library-source attribution. |
| `name:W` | The unit name is supported by a WorldBuilder filename association. |
| `name:Z` | The unit name comes from an aligned Zero Hour donor hypothesis. |
| `name:invented` | The row's structural placement holds in a unit with a generated filename. |
| `padding` | This range is recorded as padding within the proposed member sequence. |

## Read the verdict

| Result | Meaning | Evidence still needed |
| --- | --- | --- |
| **MATCH** | An owned row compiled with equal comparison bytes after applying the checker's relocation treatment and name policy. Without a proven wrong reference, the row can be credited while its reference proof remains open. | Inspect reference proof and the result's scope. |
| **Proven** | A credited MATCH also passed reference verification for the checked references. | Runtime behavior, uncovered bodies and original file boundaries have separate checks. |
| **VERIFIED** | The checker found no blocker for the assigned object. It checks owned and expected emitted rows, references, compile receipts, emitted order, extra symbols, applicable checks and unresolved Draft dependencies. | Unassigned contributions and original source completeness remain open where the ledger lacks evidence. |
| **PARTIAL** | The selected compiled body differs under byte comparison. | Check the reported symbol and RVA first. For an unresolved placeholder, a near-match percentage can describe a different compiled body. |
| **MISNAMED** | An otherwise plausible emitted body conflicts with the accepted identity at that address. | Establish the real class, signature and spelling. Request a ledger correction when the ledger is wrong. |
| **WRONG_REFERENCE** | The comparison bytes agree and a relocation points to a target the checker proves wrong. The row receives no Function MATCH credit. | Identify the intended reference and the actual emitted target, including its owning data, slot or symbol. |
| **MISSING / COMPILE_ERROR** | The checker found no usable emitted body for a row, or compilation failed. | Check declarations, flags and output. Inspect current source before assuming the body is unwritten. |

Identical machine code can be shared between several source functions.
A matching target address alone does not transfer a folded function's name
to another slot or class. Read the relocation details and relevant ownership
before changing code.

## Request a ledger change

Open an issue or put a section titled **Ledger change request** in the source
pull request. Give maintainers:

- The current base revision, exact RVA, current accepted name and owner, and
  the requested name, role, extent, alias or owner.
- Direct reference evidence such as the class's slot, one or more callers,
  parser fields, emitted symbol identity, section position or extent.
  Cite the corresponding public ancestor separately where it helped.
- The affected source files, headers, expected rows and dependent calls or
  globals. Give the check outcome and exact blocker for an existing proposal.
- Whether the source and map changes must be measured and landed together.
  For a unit move, explain both the positive path evidence and nearby
  boundaries or competing assignments.

Maintainers review and generate the ledger, expected records and source
annotations together. Keep source changes off the old identity until the
maintainer explains how the pair can be checked. An existing placeholder
can sometimes receive credit under a supported real name. Document the
evidence and let the checker and maintainer handle adoption.

## What a pull-request check covers

The check compiles changed units and units affected by changed headers,
checks the source and generated metadata rules, and compares the result
against the recorded base for losses of existing credit or proof. It reports
compile errors and failed checks. A green check is scoped to the revision,
affected units and checked rules. No pull-request result claims a successful
standalone link or game run.
